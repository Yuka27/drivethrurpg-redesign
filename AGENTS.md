## Project Overview

A client-side redesign of the DriveThruRPG storefront, built against a mock REST API.

- **Framework and build:** React 19, TypeScript, and Vite+ (`vite-plus`, the `vp` CLI), which also provides linting (Oxlint), formatting (Oxfmt), and testing (Vitest). All of it is configured in `vite.config.ts`; there are no separate ESLint, Prettier, or Vitest config files.
- **Routing:** TanStack Router with file-based routes and automatic code splitting, generated by the router Vite plugin. This is a client-only router app, not TanStack Start; do not assume server functions or SSR.
- **Data:** TanStack Query for server state (`src/api/`, with query keys centralized in `src/api/query-keys.ts`), Zustand for client state (`src/stores/`).
- **Forms:** react-hook-form with Zod schemas via `@hookform/resolvers`.
- **i18n:** i18next/react-i18next with namespaced JSON in `src/locales/<lang>/` (`en`, `pl`). `en-XA` is a dev-only pseudo-locale generated from English at runtime to expose hard-coded strings. `npm run i18n:check` fails when a locale's keys differ from English and warns about unused English keys.
- **Environment:** `src/lib/env.ts` validates `import.meta.env` with Zod at startup. `VITE_API_URL` is required; `VITE_MOCK_USER=guest` is optional and makes the mock API return the logged-out state.

### Organization

- `src/routes/`: file-based routes. Pathless layouts group pages: `_site` (standard header/footer shell), `_auth` (requires login: a guest is sent to `/` with the login modal open, and continues to the page they wanted once signed in), `_focus` (minimal chrome for checkout and order confirmation). Login, register, forgot and reset password exist only in the auth modal; there are no pages for them. `src/routes/_site/index.tsx` is still the starter placeholder.
- `src/components/ui/`: shadcn/ui primitives (new-york style, on `radix-ui`). Add new ones with the shadcn CLI per `components.json` rather than hand-writing them.
- `src/components/site/`, `src/components/title/`, `src/components/animations/`: shared app components.
- `src/features/<feature>/`: feature-specific UI and logic. `auth`: login, register, and forgot/reset password in `password/`. `account`: the account area (`/account` routes): sidebar/hub navigation, balance card, and the settings cards, built on `SettingsCard`/`SettingsRow` in `settings-card.tsx`. Account pages wrap their content in `AccountPage` (mobile breadcrumb, title, subtitle) and use `SearchField` (`components/site/search-field.tsx`) for list search and `OptionSelect` (`components/site/option-select.tsx`) for sort/filter selects. Auth views share their input, title and button classes from `auth/shared/styles.ts`. Buttons whose flow is not built yet call `useComingSoon()`; replace each when its flow exists.
- Account preferences (`/account/preferences`) save on every change through `useUpdateAccountPreferences` (optimistic, rolled back on failure). `GET /account/preferences` is cached under one key with one full schema (`src/api/preferences.ts`), shared with language detection; do not add a second schema for it. Language, currency and AI content are edited through the preferences store, never patched directly. Theme (`useThemeStore`) is stored on the device for everyone; for a logged-in user `usePreferencesSync` also saves it to `display.theme` and applies the account's theme once per login.
- Orders (`/orders`): `/orders` returns only summaries, so each card loads `GET /orders/{id}` (lines, payment) and `GET /titles/{id}` per line (`useTitleName` in `api/titles.ts`, cached under `queryKeys.titles.name`, never `titles.detail`; cart and confirmation lines use it too). Date/status filters, search and paging (5 a page, `components/site/pagination.tsx`) run in the browser over the whole history because the API has no such filters. They live in the URL (`orders-search.ts`: `/orders?period=all&status=paid&q=&page=2`, defaults stripped) and the last list viewed is remembered in memory (`useLastOrdersSearch`), so the order page's "← Orders", the sidebar/hub "Orders" links and browser Back all return to the same list.
- Order detail (`/orders/$orderId`, by order number): progress from the order's status and `digitalReady`; each item's button comes from the library (`useLibraryByTitle`): new/updated file → Download, otherwise "In library", not owned → none. Files the API only reveals after a request (invoice, downloads) open through `openInNewTab` (tab opened inside the click so pop-up blockers allow it).
- Library (`/library`): `useLibrary()` loads the whole library once (`GET /library?pageSize=100`, one cache entry shared with the order page's `useLibraryByTitle`) and the page filters, sorts and pages it in the browser (`features/library/library-filters.ts`), because the API filters only one value per facet and its facet counts ignore the other filters. Filters live in the URL (`library-search.ts`: `/library?status=updated&system=osr,d20_5e&format=pdf&q=&sort=title&page=2`; multi-select values comma-joined via `listParam`/`splitList`/`joinList`, defaults stripped), and the last view is remembered in memory (`useLastLibrarySearch`) for the header's "My Library" link. Counts are live: each facet counts under all other filters but its own picks. A title with one file downloads it; several files, or several selected titles, go through `POST /library/download-bundle` (polled until ready). Downloading an updated title calls `mark-updates-seen`. The design's Genre and Language groups and the "Not downloaded"/"Archived" statuses are left out: the library data has no such fields.
- Listing (`/titles`, `features/listing/`): filtering, sorting and paging run in the API (`GET /titles`, 20 a page); comma-joined values mean "any of" there too, and `priceMax` goes in minor units (the URL keeps whole units: `?priceMax=10`). Facet counts come from `GET /titles/facets`, which counts under every filter including the facet's own picks, so `useListingFacets` asks again without them for each facet in use. Filters, sort, view (`grid`/`list`) and page live in the URL (`listing-search.ts`); a page change is a history entry, filter changes replace it. The banner is the first `GET /home` banner. Cards add to the cart through the title's first edition SKU (cards carry none: `useAddTitleToCart` fetches `GET /titles/{id}`); owned titles link to the library; the heart asks guests to log in. Title card pieces (`TitleCard`, `TitleRow`, `RatingStars`, `TitlePrice`, `WishlistButton`, `CartButton`) are in `components/title/` for reuse (home, search). Genre is a facet like the others (`?genre=`, `genres` in `/titles/facets`) and hidden while the API returns no genres. Not built for lack of API data: the Rating filter, a price "from".
- Home (`/`, `features/home/`): the banner (`components/site/promo-banner.tsx`, shared with the listing), "Discounts & Promos" from the `GET /home` "sale" section, tabbed lists from its "new", "bestselling", "sale" and "free" sections (a tab only when it has titles; desktop previews the hovered/focused title, fetching its detail), "Featured for you" as the three rule systems with the most titles (the API has no genres), the catalogue numbers, the top publishers, "Under $5" (phones only, as in Figma) and "Recently Viewed". `GET /home` has one schema (`useHomeBanners`/`useHomeSections` select from it). "Recently Viewed" (`stores/recently-viewed.ts`, `components/title/recently-viewed.tsx`) is kept on the device: the product page records each title opened; home, listing and product pages show it. Not built for lack of data: "Popular Upcoming", the promo campaign art and labels.
- Cart (`/cart`, `features/cart/`): `GET /cart` with lines, promo, gift and totals (`api/cart.ts`); every change (`PATCH`/`DELETE /cart/items/{lineId}`, `POST /cart/undo`, `POST`/`DELETE /cart/promo`, `PUT /cart/gift`) answers with the whole cart, which replaces the cached one, and refetches `GET /me` for the header badge. Lines have no publisher, so each loads the cached `useTitleName`. A download gets a quantity stepper only once it has more than one; printed lines always do. Removing offers Undo through the response's `undoToken`. The gift card saves on leaving a field once the recipient's email is valid; checkout stays disabled until a gift has that email. The API keeps no recipient name: it is sent as `recipientName` for when it does. "Proceed to checkout" links to `/checkout`. Phones get a bar stuck to the bottom of the cart (sticky, so it never covers the footer) with the total and "Checkout"; the summary card stays on the page too, without its button. "Customers also bought" is `GET /cart/recommendations` in `ShelfCard`s (`components/title/shelf-card.tsx`, shared with home's "Under $5"). The desktop nav row shows "Back to Home" here, as on the listing.
- Wishlist (`/wishlist`, `features/wishlist/`, login required): the listing's layout, filter panel (`ListingFilterPanel` with `languages={false}`), mobile filter sheet and chips (`useAppliedFilters`, shared with the listing) over the saved titles. `GET /wishlist` only pages, so `useWishlist()` loads it whole (`pageSize=100`) and `wishlist-filters.ts` filters, counts (each facet under every filter but its own), sorts (date added, price, title) and pages in the browser; the URL carries the listing's filter names (`wishlist-search.ts`). Items become `TitleSummary`s (`toTitleSummary`; no ratings or text language in the data) for the listing's cards and rows. "Add all to cart" and the sale banner's "Add sale titles to cart" send `POST /wishlist/add-to-cart` with what is neither owned nor in the cart. Share is a dialog over `GET`/`PATCH /wishlist/settings`: nothing goes public without its switch. Removing with the heart (anywhere) offers Undo through the `undoToken` `DELETE /wishlist/items/{id}` returns. There is no public wishlist page yet (the share link is the API's own address).
- Checkout (`/checkout`, `features/checkout/`, mockup `docs/Checkout — DriveThruRPG.html`): one page of numbered sections (contact, billing/shipping address, delivery for printed items, payment, gift) beside a sticky summary that folds to one line on phones; the Pay button submits the form from the summary (`form="checkout-form"`). `POST /checkout` starts a session per visit (`useCheckoutSession`, a query that is never refetched); picking a shipping rate saves it at once (Standard by default) so the total stays live. A guest types email and address; an account sees its default address and card (`/account/addresses`, `/account/payment-methods`) as one-line summaries with Change / Use another. Pay runs the provider's steps in order (`usePlaceOrder`: contact, addresses, payment intent, place order). There is no payment provider: the card fields are validated (Luhn, expiry, CVC) but never sent; only a stand-in method id goes out, and Stripe's decline test card 4000 0000 0000 0002 maps to the mock's `pm_declined`, which shows the declined banner (focused, nothing charged). The rules depend on the buyer (`checkoutSchema`). What the confirmation needs that the order lacks (receipt email, which titles ship) passes through the in-memory `useCheckoutResult`.
- Order confirmation (`/order-confirmation/$orderNumber`): the order (`useOrder`), the facts, each line with "PDF ready" and a shipping line for printed copies, and the library's Download / In library button for an account (`LibraryButton` from the order page). A guest (`order.guest`) gets the optional "Keep these in your Library" password step (`POST /orders/{id}/create-account`), then a login with the email prefilled. It waits for `/me` before choosing the guest or account version. The minimal `_focus` header shows "Secure checkout" and "Back to cart" on the checkout, "Continue shopping" after it.
- Gift claim (`/gift/$token`, `features/gift/`, mockup `docs/Gift Claim Page — DriveThruRPG.html`): `GET /gifts/{token}` (`api/gifts.ts`) decides the view. Ready: the gift (from, message, titles) beside a claim card: logged out, "Create account" / "Log in" tabs with the gift's email prefilled (register or log in, then `POST /gifts/{token}/claim`), or Google / Facebook / Roll20 below either tab (the auth modal's `SocialButtons`, then the claim); logged in, the account and one "Claim gift". Claimed by you: the downloads (`LibraryButton`) and an optional thank-you (`POST …/thank-you`). Claimed by someone else, expired (`POST …/resend-link` to the masked email) and a broken link (404: enter the code, `POST /gifts/lookup`, then the gift's page). A claim may answer with a session (`signIn`, exported from `api/auth.ts`); its `user` is parsed leniently because the API sends `avatar: null`. Buttons waiting on a request show `Spinner` (`components/ui/spinner.tsx`) and say what they wait for ("Creating your account…", "Claiming your gift…"). Signing in swaps the logged-out card for the logged-in one mid-claim, so the claim has a mutation key and `useIsClaiming(token)` lets either card show it; a failed sign-in stays on the form (`FormAlert` or the field), a failed claim is a toast. The two columns align to the top.
- Empty and error states (`components/site/empty-state.tsx`, mockup `docs/Empty and No-Result States — DriveThruRPG.html`): `EmptyState` (icon in a circle, heading, one line, then actions via `EmptyActions`, `EmptyLabel`, `EmptyLink`) and `ErrorState` (retry, support, status) replace one-line messages: say what happened, one primary action, a way to recover. In use: listing "filters too narrow" (`listing-empty.tsx`: clear all, or remove one filter with the count it brings back via `useTitleCounts`), library empty and no match (`library-empty.tsx`), empty cart with "Saved for later" (`POST /cart/saved/{lineId}/move-to-cart`), empty wishlist with popular picks (the bestsellers: the API has no wishlist ranking), no orders and no follows (`account-empty.tsx`; follows suggest the publishers with the most titles in the library), the 404 and root error page (`__root.tsx`, inside the site header and footer), and a title withdrawn from sale (`title-unavailable.tsx`: an owner's copy is safe, similar titles instead). Search has its own "No results" (`features/listing/search-results.tsx`) and the notifications panel its "all caught up".
- Notifications (`components/site/notifications-popover.tsx`, Figma "Notifications"): the header's bell (unread count from `GET /me`) opens a popover, full width under the header on phones. `GET /notifications` (`api/notifications.ts`) loads when it opens; each row shows the type's icon (outlined red while unread), the title in bold, the body and the day ("Yesterday", "2 Oct"). Opening one marks it read (`POST /notifications/{id}/read`), closes the panel and goes to its link (`appLink` turns `/library?view=updated` into `?status=updated`); "Mark all as read" is `POST /notifications/read-all`. Both are optimistic and refetch `/me`. Empty: "You’re all caught up". "Notification settings" opens `/account/preferences#email-notifications`.
- Search (mockup `docs/drivethrurpg-search-dark.html`): the header's field (`components/site/search-bar.tsx`) is a combobox with a suggestion panel. Empty: recent searches (`stores/recent-searches.ts`, on the device, last 5) and popular ones (`GET /search/popular`). Typing (debounced): suggested searches, titles and publishers from `GET /search/suggest`, the words highlighted, then "See all results"; a loading skeleton and "No quick matches". ↑ ↓ move (`aria-activedescendant`), Enter picks or searches, Esc and a click outside close. Desktop: a panel under the field over a dimmed page; phones: full screen with a back button. A title opens its page, a publisher the listing filtered by it, anything else `/search?q=`. The results page (`routes/_site/search.tsx`) is the listing in `mode="search"`: the same filters, chips, sort and paging (`q` is a listing parameter, so facets and "loosen one" counts include it), with items from `GET /search`, "Results for “q”", the count, matching publishers to follow, and, when the words match nothing, "No results" with the API's `didYouMean`, tips and popular searches.
- Naming: `TitleSummary` (`api/titles.ts`) is a title as lists return it (card, row, shelf); `TitleDetail` is the product page's; `TitleCard` is only the card component. In the cart, `CartLine` is the API's line and `CartItem` the component showing one; the cart's gift switch is `GiftOption` (`features/gift/` is the gift claim page). Links to main-site pages the redesign lacks (support, terms, privacy, status, app download) are named in `config/links.ts`, all `TODO_URL` (`'#'`) until known.
- Header nav (`components/site/site-nav.tsx`, desktop; "Browse"/"More" accordions in `mobile-menu.tsx`): Publisher, Genre, Product Type, Rule System and Format menus list each facet's top values from `GET /titles/facets` (`use-browse-groups.ts`), each a link to `/titles` filtered by it; a facet with no values (Genre, until the API has genres) is left out. On the listing (`/titles`) the desktop row shows "Back to Home" in place of those menus. Community, Information and Support link to the main site (`config/utility-menus.ts`, hrefs still `TODO_URL` where unknown); on a product page they move into its sticky menu. Publisher links everywhere open `/titles?publisher=<id>`; there is no publisher page.
- Product page (`/titles/$titleId`, `features/title/`): `GET /titles/{id}` (editions with SKUs, prices, stock, shipping) plus `/reviews` (with the 1-5★ histogram), `/discussions`, `/similar` ("Customers also bought") and `/samples`, each under `queryKeys.titles.related`; the publisher card and follow switch use `api/publishers.ts` (`POST/DELETE /publishers/{id}/follow`). The header card leads with `shortDescription` (plain text, left out when the API has none) and Overview gives the whole `description` (paragraphs split on blank lines), so neither repeats the other. The buy card adds the chosen edition (`useAddEditionToCart`; "Buy as a gift" also sends `PUT /cart/gift`); an owner of the digital edition gets "In your library" instead, and `available: false` disables buying. Reviews and discussion threads are merged into one list, newest first, 5 a page. Replying, flagging and starting a discussion have no API: they call `useComingSoon` (`lib/use-coming-soon.ts`). Not built for lack of data: the title logo art, "For Dungeon Masters", thread replies, following an imprint or rule system, "Show full credits", "Recently viewed". The tabs are in-page links to the three sections. The sticky secondary menu (`features/title/product-sticky-nav/`, from the prototype `docs/drivethrurpg-product-sticky-menu-dark.html`) sticks under the site header (`--header-h`, set by `SiteHeader` through `useHeightVar`): a breadcrumb row (publisher → rule system, the API has no product line → title) with the utility menus, then a product bar (cover, title, section tabs, price, Add to Cart) that slides open once the page's `<h1>` has left, watched by an IntersectionObserver, and is `inert` while closed. The bar sits out of the flow, so the page never shifts. Scroll-spy (`use-scroll-spy.ts`, one check per frame) drives both its tabs and the page's own; sections use `scroll-margin-top: calc(var(--header-h) + var(--stick-h) + 12px)`. The chosen edition lives in `TitlePage` (`use-buy.ts`), so the buy box and the bar show and add the same one. Below 700px: back link + "⋯" menu, and a two-row bar with scrolling pills. Adding to the cart refreshes `GET /me` too, for the header's cart badge.
- Filters (`src/components/filters/`): data-agnostic building blocks for the library now and the product listing later: `FilterGroup` (collapsible section; `variant="sidebar"` open with "(n)", `"sheet"` closed with "n selected"), `CheckboxFacet` (5 values then "+ N more", optional search box), `RadioFacet`, and `FilterSheet` (mobile "Filters" button + bottom sheet; changes apply live), plus `AppliedFilters` (removable chips, "+ N more", "Clear all") and `QuickFilters`. Counts are optional (`FacetOption.count`) for values the API does not count (price bands, languages). The router keeps commas unencoded in URLs (`stringifySearch` in `main.tsx`). They take `FacetOption` (`{ value, label, count }`) arrays, so API facets (`/titles/facets`) plug in as they are. Facet value labels are in `listing:facets.<facet>.<value>` with the API value as fallback. `createSearchMemory` (`lib/search-params.ts`) is the shared "remember the last list view" store (Orders and Library use it).
- Activity pages outside `/account` (`/following`, `/orders`) wrap themselves in `AccountShell` (sidebar on desktop) and show `AccountBreadcrumb` on mobile, so they look like part of the account area.
- Loading states: nothing loads into a blank page. `Skeleton` (`components/ui/skeleton.tsx`, the shadcn primitive, `bg-muted`, hidden from screen readers, still under reduced motion) draws the shape of what is coming, and one `LoadingStatus` per loading region says "Loading…" to screen readers. Shared outlines: `TitleCardSkeleton`/`TitleRowSkeleton`/`TitleResultsSkeleton` (in the listing's chosen view), `ShelfCardSkeleton`/`ShelfSkeleton` (`components/title/title-skeletons.tsx`), `FilterPanelSkeleton` (`components/filters/`), `SettingsRowsSkeleton` (`settings-card.tsx`) and `PageSkeleton` (`components/site/page-skeleton.tsx`: the router's `defaultPendingComponent`, and inside the site shell while `_auth` checks the login). Page-specific outlines sit next to the page (cart, checkout, confirmation, gift, product page, orders, library card, home sections). A section shows its skeleton while its query is pending and disappears only once it is known to be empty; header pieces (browse menus, notifications, search panel and popular searches) do the same.
- Mutations that update a list optimistically refetch in the background in `onSettled` (`void queryClient.invalidateQueries(...)`, not `return`): returning the promise makes React Query hold back the caller's own callbacks (toasts, Undo) until the refetch finishes.
- Account URLs: on desktop `/account` shows the sidebar plus the Account settings; on mobile it is the "My account" hub, and the settings live at `/account/settings` (desktop shows the same page there). All auth screens open in one modal (`auth-dialog.tsx`), switched through `useAuthDialogStore` views `login | register | forgot | reset`.
- `src/components/site/testing-links.tsx` is a temporary "Testing" section in the footer that opens screens normally reached only from emails: the password-reset link (valid or expired) and the gift link in each state the mock knows (`tok_ready`, `tok_claimed_by_me`, `tok_claimed`, `tok_expired`, and any other token for a broken link). The project sends no real emails; remove it once those links exist.
- File names are kebab-case everywhere (`login-form.tsx` exports `LoginForm`), enforced by `unicorn/filename-case`. Route files are exempt because TanStack Router derives URLs from their names.
- `src/api/`, `src/lib/`, `src/stores/`, `src/i18n/`, `src/config/`: API hooks, utilities, stores, i18n setup, and static config.
- `src/router.ts` builds the router (`createAppRouter`: readable commas in URLs, `PageSkeleton` while a route gets ready); `main.tsx` and the routing tests use it. The root route's error page brings its own tooltips, auth modal and toasts (`AppChrome`) because it replaces the root component, and its "Try again" calls `router.invalidate()` so a failed login check runs again.
- `src/routeTree.gen.ts` is generated by the router plugin on `vp dev` / `vp build`. Never edit it by hand.
- Imports use the `@/*` alias for `src/*` (`#/*` also resolves, but `@/` is the convention).

## Figma/MCP Design Integration Rules

Use these repository-specific rules when translating a Figma design into this codebase. Treat Figma output as a reference to adapt, not code to copy wholesale. Before using Figma MCP design-to-code tools, load the required `/figma-design-to-code` skill and follow its workflow. Reuse existing project conventions and design-system matches; do not invent a parallel system when one already exists.

### Current Design-System State

- **Tokens:** All design tokens live in `src/styles/index.css` as shadcn-style CSS variables: light values on `:root`, dark values on `.dark`, mapped to Tailwind utilities through `@theme inline` (`bg-background`, `text-muted-foreground`, `bg-primary`, `text-success`, `text-warning`, `bg-update` (the lime "Updated" badge), and so on). Dark is the designed, default theme. Several values carry comments naming their Figma source. There is also a radius scale (`--radius` = 10px), `--shadow-popover`, and an `animate-shimmer` animation.
- **Typography:** `font-sans` is Inter and `font-heading` is Sora, loaded from Google Fonts in `index.html`. Headings use `font-heading` through base styles.
- **Layout:** a custom `container` utility gives the mockups' 1240px max width with 24px gutters. Breakpoints are Tailwind defaults; none are customized.
- **Components:** shadcn/ui primitives in `src/components/ui/`, styled with `class-variance-authority`, merged with the `cn()` helper from `src/lib/utils.ts` (clsx + tailwind-merge). No Storybook.
- **Icons:** `lucide-react`, the icon library declared in `components.json`. Keep icon-only controls labeled for assistive technology.
- **Assets:** brand logos in `src/assets/logos/` and social login icons in `src/assets/social/`, imported through Vite. There is no `public/` directory; add one only for files that need stable root-relative URLs.
- **Animation:** `tw-animate-css` for enter/exit utilities. Respect reduced motion (see `src/lib/use-reduced-motion.ts`).
- **Toasts:** `sonner`, mounted once in `src/routes/__root.tsx`.

### Token and Styling Rules

1. Check `src/styles/index.css` and the existing `ui/` components before introducing design values. Map Figma variables to the existing semantic tokens first.
2. If a value belongs to the visual system and no token fits, add it centrally in `src/styles/index.css`: a CSS variable in both `:root` and `.dark`, plus a `@theme inline` mapping so it generates a utility. Use semantic names, not raw hex values scattered through components.
3. Keep one-off values local (Tailwind arbitrary values) only when they are truly exceptional.
4. Styling is Tailwind utility-first. Do not add CSS Modules, CSS-in-JS, or a token transform pipeline (such as Style Dictionary).

### Components, Routes, and Assets

- Register routes with `createFileRoute` in `src/routes/`, under the layout group that matches the page's shell.
- Extend or compose the shadcn primitives before building a new control. Put genuinely shared UI in `src/components/`, and keep feature-specific UI in `src/features/<feature>/`.
- Use typed function components, semantic HTML, and `useTranslation()` for all user-facing text. Add new strings to both `en` and `pl` locale files.
- Import component and page assets from `src/assets/`. Give informative images meaningful alt text; decorative images get empty alt text.

Route shape:

```tsx
import { createFileRoute } from '@tanstack/react-router'

export const Route = createFileRoute('/_site/search')({ component: Search })

function Search() {
  return <main className="container">...</main>
}
```

### Figma MCP Handoff

1. Inspect the target Figma node with the Figma design-to-code workflow, including its screenshot/context and available variables or component mappings when relevant. Confirm the target frame, responsive states, and interaction states rather than implementing from a partial screenshot.
2. Map Figma colors, typography, spacing, radii, and effects to the existing tokens in `src/styles/index.css`, in both light and dark themes.
3. Reuse existing React, TanStack Router, shadcn/ui, lucide, and Tailwind conventions. Do not add a second UI framework, CSS methodology, icon system, or token transformer to mirror the design file.
4. Bring over only required assets. Keep asset references local and build-compatible. Do not silently replace meaningful product imagery with generic placeholders.
5. Match the design across required breakpoints and states, then validate layout, keyboard/accessibility behavior, and asset loading in the running app.

## Commands and Conventions

- `npm run dev`: dev server on port 3000 (`vp dev`).
- `npm run build` / `npm run preview`: production build and local preview.
- `npm run typecheck`: `tsc --noEmit`.
- `npm run lint`: Oxlint via `vp lint`, type-aware. `npm run format` formats and applies lint fixes.
- `npm run check`: formatting check only (`vp fmt --check`).
- `npm test` / `npm run test:watch` / `npm run test:ui`: one run, watch mode, or watch mode with coverage and the Vitest UI in the browser. `npm run test:coverage` runs once with coverage (summary in the terminal, HTML report in `coverage/`). `@vitest/ui` and `@vitest/coverage-v8` stay pinned to the Vitest version bundled with `vite-plus`. Vitest runs with jsdom; tests match `src/**/*.test.{ts,tsx}` and sit next to the code they test. Import test APIs from `vite-plus/test`, not `vitest`. Components are tested with Testing Library (`@testing-library/react`, `user-event`, `jest-dom` matchers), querying by role and visible English text.
- Test helpers in `src/test/`: `setup.ts` (runs before every file: jest-dom, English i18n, jsdom stubs, cleanup of storage and the auth token), `render.tsx` (`renderWithProviders`: fresh React Query cache plus a memory router so `<Link>` works; `renderInDialog` for the auth views, which use `DialogTitle`/`DialogDescription` and so need a Dialog around them), and `api.ts` (`mockApi` fakes `fetch` per `"METHOD /path"`; handlers get the request `body` and query `params`, and `bodies()`/`params()` return what was sent; plus `apiError`, `session`, `user` and `cart` fixtures), and `app.tsx` (`renderApp(url)`: the whole app on the real route tree, `createAppRouter` from `src/router.ts` with a memory history and the app's own query client; `mockApp` fakes what every page asks for, so a test adds only its page's requests). Routing itself (which page a URL opens, the login check, 404 and error pages, filters in the URL and history) is tested in `src/routes.test.tsx`, outside `src/routes/` so the router plugin does not take it for a route. Never let tests hit the real API.
- `npm run i18n:check`: validates locale files.
- A pre-commit hook (`.vite-hooks/pre-commit`, installed by `vp config` on `npm install`) runs `vp staged`, which runs `vp check --fix` on staged files.
- Formatting: no semicolons, single quotes, trailing commas, 80-character lines.
- Notable lint rules: kebab-case file names, `Array<T>` instead of `T[]`, `import type` for type-only imports, imports at the top of the file.
- Intent: `@tanstack/intent` is a dev dependency. `npm exec --no -- intent list` surfaces version-matched skills from installed TanStack packages (Router core and its sub-skills, the router plugin, virtual file routes).
